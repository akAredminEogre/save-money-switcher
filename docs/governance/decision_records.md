# 決定記録（殿裁可 ADR 集：論点1〜11・A〜G・N-1〜N-4・E-3残・撤回履歴）

## 1. Overview

本書は `save-money-switcher`（SAVE MONEY 方式の家族クイズ操作盤）に対して殿が下された全裁可を、Architecture Decision Record（ADR）として一元記録する統制文書である。要件本体 `req:save-money-switcher-requirements`（status: approved, confidence 0.95）を唯一の真実源とし、そこに現れる各裁可（論点1〜11・A〜G・N-1〜N-4・E-3残）と撤回履歴を、実装フェーズが参照可能な確定入力に落とし込む。ここに記された 🟦 確定値は改変禁止であり、これに反する実装はリリース不可（release-blocking）として扱う。

### 1.1 目的と位置づけ

- 各決定の「何を・いつ・なぜ確定したか」「却下/撤回された対案」「影響を受ける実装モジュール」「実装上の帰結」を1件1 ADR として保存する。
- 壁打ち（要件定義）フェーズは 2026-08-15 の N-1・N-4 裁可をもって完了済み。殿判断待ちの論点は残っておらず、本書は実装組み立てフェーズの拘束仕様として機能する。
- 未確定として明示的に残るのは技術選定4点（ホスティング/インフラ・DB 永続化技術・実装言語・家族限定アクセス制御）のみで、これらは §3 Follow-ups に集約する。

### 1.2 凡例（決定ステータス）

| ステータス | 意味 |
|---|---|
| **確定（🟦）** | 殿裁可済・改変禁止の確定入力。実装はこれに従う。 |
| **改定** | 一度確定した後、後続裁可で内容が上書きされた（撤回とは異なり決定自体は生きている）。 |
| **撤回** | 前提そのものが破棄された。撤回済前提での実装はリリース不可。 |
| **廃止** | 後続要件により論点そのものが消滅した（判断不要）。 |

### 1.3 リリースブロッキング不変条件（release-blocking invariants）

以下3件は本プロジェクトの非交渉制約であり、違反する成果物はリリース不可である。各 ADR 本文でも該当箇所に再掲し統制を効かせる。

1. **`module:realtime_sync` — クラウド実行・当日インターネット接続のみが有効。** 旧オフライン LAN 前提（論点2）は 2026-08-08 に撤回済であり、ホスト PC をサーバ/アクセスポイント化する実装・`localhost` LAN 完結を前提とする実装は禁止。同期はクラウド上の WebSocket サーバが担い、当日インターネット接続を前提とする（→ ADR-論点1 / ADR-論点2 / §3.1）。
2. **`module:scoring` — 得点ルール確定値は改変禁止。** 先渡し **10,000 円**／誤差1につき **−100 円**（誤差 × −100 円）／ピタリ賞（誤差0）で他プレイヤーから **1,000 円横取り**／**1ゲーム10問**／**残額最多が勝ち**。旧軍師推奨の「点化」「500 点」「現金感を薄める」は**無効**であり、内部表現・表示とも「円」を基調とする。ポイント等への置換は禁止（→ ADR-B / ADR-C / ADR-得点方式 / ADR-N-4）。
3. **`module:config` / `module:participants` — 接続上限はハードコード禁止・設定外出し。** 同時接続タブレット上限の既定値は **8 台**だが、コードに定数リテラル `8` を埋め込んではならない。上限は設定パラメータ（`MAX_TABLET_CONNECTIONS`）として外出しし、上限超過時の接続拒否は設定値を参照して機能すること。8→16→32 への引き上げは非改修で可能とする（→ ADR-論点10）。

### 1.4 実装規約（TypeScript / Vitest / レイアウト / モジュール指定子）

本プロジェクトの実装言語・ツールチェーンはハーネス scaffold により固定されており、本書のすべての例・パス・型はこれに厳密に従う。

- **実装言語 = TypeScript のみ。** 本書に現れるファイルパス・モジュール構成・依存管理・ツールチェーン参照はすべて TypeScript 慣行のみを用いる。他言語の拡張子・マニフェスト・ツールは例示・フォールバックとしても登場させない。要件が挙げた選定軸「クラウドへデプロイでき WebSocket 等を扱える」の解として **TypeScript / Node** を採る（要件の例示に一致）。
- **テストランナー = Vitest（固定・release-blocking のグラウンドトゥルース）。** verify コマンドが実際に走らせるのは Vitest であり、本書はこれを再解釈・上書きしない。テスト記述の例はすべて Vitest 自身のテスト宣言 API（`import { describe, it, expect } from "vitest";`）を対象とする。仮に本プロジェクトで「サードパーティ依存を最小化する」方針が語られても、それは**出荷コードのランタイム依存**を統べるものであってテストランナーには及ばない。依存数の哲学を根拠に別のテストフレームワークや Node 組み込みの `node:test` を用いてはならない。
- **レイアウト契約（release-blocking・出力パス fence が implement 時に強制）。**
  - **テスト配置**: 著すテストファイルおよび本書が参照するテストパスは、すべて `tests/` 直下に置く。`test/`・`spec/`・`specs/` 等の別ディレクトリを発明しない。`tests/` 外のテストは fence に落とされ、宣言した「テスト」成果物が未生成扱いとなりビルドが落ちる。
  - **ソース配置**: 著すソースモジュールはすべて `src/` 下に置く。`src/` 外のソースは fence に落とされる。
  - **ハーネス所有 scaffold**: 依存マニフェスト・ロックファイル・ランナー/ツール設定（`package.json`・`package-lock.json`・`tsconfig.json`・`vitest.config.ts`）はハーネスが既に用意しており、本書はこれらを成果物として著さない・宣言しない。
- **モジュール指定子の一貫性（NodeNext/Node16・native typecheck が強制）。** すべての相対 import 指定子は、**出力される `.js` ファイル名を明示した拡張子**を伴う。`import { x } from "./x.js"` と書き、`"./x"` や `"./x.ts"` は書かない。再エクスポート（`export { x } from "./x.js"`）・デフォルト/名前空間 import・型のみ import（`import type { T } from "./x.js"`）にも同一に適用する。拡張子を欠く相対 import は TS2835 でコンパイル不能となる。

### 2.1 アーキテクチャ・実行形態

#### ADR-論点1 — 同期方式 = クラウド WEB アプリ（2026-07-25 確定／2026-08-08 改定）

- **決定**: プロダクトは WEB アプリとして構築する。**クラウド上のサーバ**へ制御盤（`role: host` のホスト画面 `/control-panel`）・TV 表示（`/tv`）・各解答者端末（`role: answerer` のタブレット `/tablet`）を接続し、インターネット経由の WebSocket でリアルタイム同期する。ホスト PC はサーバにしない。
- **却下（🟦・単独では第二要件を満たせない）**: (a) 同一 PC 2ウィンドウ＋`localStorage`/`BroadcastChannel`、(b) Presentation API 単独。いずれも別端末（解答者タブレット）を同一同期網に載せられない。
- **改定履歴**: 当初は「ローカルサーバ＋WebSocket（ホスト PC がサーバ）」として整理していたが、2026-08-08 の殿御下命でクラウドサーバ構成へ改めた。
- **影響モジュール**: `src/realtime_sync/`（クラウド WebSocket）・`src/control_panel/`・`src/tv_display/`・`src/tablet/`。
- **帰結**: 同期実装（`answers_opened`・`answer_revealed` 等のイベント配信）はクラウド側 WebSocket を単一の権威とする。**リリースブロッキング不変条件1** により、`module:realtime_sync` はホスト PC をサーバ/AP 化する実装を含んではならない。

#### ADR-論点2 — オフライン前提の撤回（2026-07-25 確定→2026-08-08 撤回）

- **撤回内容**: 旧確定「オフライン開催前提／会場ネット不通でも動作／外部依存なしで完結／ホスト PC をローカルサーバ兼 AP とする」は 2026-08-08 の殿御下命（`followup_20260808_lord_premise_change_cloud`）により全撤回。
- **現行の確定前提（🟦）**: クラウドで実行する／ホスト PC をサーバにしない／**本番当日のインターネット接続を前提とする**。回線断はオフライン完結ではなく運用リスクとして扱う。
- **影響モジュール**: `src/realtime_sync/`・`src/config/`。
- **帰結（release-blocking）**: 撤回済前提（LAN/AP/オフライン完結）を復活させる実装はリリース不可。回線断対策は運用側（バックアップ回線・テザリング等の当日回線確保）で担保し、コードは当日接続前提で組む（→ §3.1）。**リリースブロッキング不変条件1** に直結。

#### ADR-E-2（アーキ側面）— 形態 = クラウド実行 WEB アプリ・問題は DB 保持（2026-07-28 確定／2026-08-08 クラウド整合）

- **決定**: 本作は**クラウド上で実行する WEB アプリ**である。問題は事前ファイルから読み込み **DB 登録**し、ランタイムは DB から供給する。DB の具体永続化技術のみ greenfield 時に選定（→ §3.1）。
- **影響モジュール**: `src/questions/`（DB `questions` テーブル）・`src/realtime_sync/`。
- **帰結**: クラウド実行と整合する範囲で DB を選ぶ。データ入稿・ライブ編集の詳細は §2.4 の E-1/E-3/E-3残/N-2 に従う。

### 2.2 ゲーム骨格・題材

#### ADR-論点3 / 論点3細目 — 数値当て系・MVP は1形式（2026-07-25／2026-07-26 確定）

- **決定**: ゲーム骨格は数値当て系（参考形態＝フジテレビ『賞金先渡しクイズ SAVE MONEY』を家族で遊ぶ形）。**MVP は SAVE MONEY 型の1形式に絞る**。他形式・複数形式拡張は初版スコープ外。
- **帰結**: `src/control_panel/`・`src/tv_display/` はこの1形式の操作盤/提示面を最優先で作り込む。

#### ADR-論点4 — 名称・題材（2026-07-26 確定）

- **決定**: 題材を「節約」に寄せない。『節約(価格当て)』は本プロダクトと無関係。題材基準は Wikipedia『賞金先渡しクイズ SAVE MONEY』記載の**番組のゲーム形式**（賞金先渡し→誤答で減算）。本プロダクトは「SAVE MONEY 方式の家族クイズ操作盤」であり、名称の SAVE MONEY は**参考番組名由来**で節約テーマを意味しない。
- **帰結**: UI 文言・出題内容とも節約/価格当てに寄せない。

#### ADR-D — 題材ジャンル（2026-07-27 確定）

- **決定**: **0〜100 の数値で答えられれば何でも可**（数値当て全般・家族ネタ/雑学/統計自由）。節約/価格当てには寄せない。
- **帰結**: 出題データ（`questions.correct_value`）は 0〜100 の整数を正解値として保持する（G と整合）。

### 2.3 得点・賞金ルール（`module:scoring` — release-blocking 不変条件2）

#### ADR-得点方式 / ADR-A / ADR-B / ADR-C / ADR-G

- **得点方式（2026-07-26 確定）**: 案A（SAVE MONEY 準拠）。「賞金先渡し → 誤差に応じて減算 → 残額最多が勝ち」。
- **A. ゲーム形式（2026-07-27 確定）**: **個人戦**（チーム戦ではない）。1人1台のタブレット（入力専用）で各自回答。
- **B. 得点/賞金ルール（2026-07-27 確定・改変禁止）**:
  - 先渡し **10,000 円**（ゲーム開始時に各プレイヤーへ配分）。
  - 正解値との**誤差1につき −100 円**（誤差5 → −500 円）。
  - **ピタリ賞**: 誤差0 で**他プレイヤーから 1,000 円を獲得**（横取り）。
  - ★設計原則「現金感を薄めない」: 金額は抽象化せず円を前面に出す。**ポイント/点への置換は禁止**（表示・内部表現とも「円」基調）。
  - **是正（重要）**: 2026-07-26 の旧軍師推奨「先渡し1万**点**／ピタリ賞500点／現金感を薄める」は殿裁可により**却下・無効**。金額を「点」化する記述・現金感を薄める記述は無効。
- **C. 問題数（2026-07-27 確定）**: **10問**（スペシャル準拠。旧推奨「5問」から更新）。
- **G. 入力仕様（2026-07-28 確定）**: **0〜100 の整数限定・小数不可**。入力・判定・スコアリングのすべてで整数のみ受理。誤差 = |回答 − 正解| は常に 0〜100 の整数、減算額 = 誤差 × 100 円 も常に整数円。小数・マイナス・100 超は UI／サーバ双方で拒否。
- **影響モジュール**: `src/scoring/`・`src/tablet/`（入力バリデーション）・DB `balances`。
- **帰結（release-blocking）**: `module:scoring` は上記確定値を定数ではなくルールとして忠実に実装し、いかなる「点」化・500点・現金感希薄化も含めてはならない。受け入れは以下の Vitest テストで固定する（`tests/scoring.test.ts`）。

```typescript
import { describe, it, expect } from "vitest";
import { applyQuestionScore } from "../src/scoring/apply_question_score.js";

describe("scoring", () => {
  it("先渡しは 10,000 円である", () => {
    expect(applyQuestionScore({ balance: 0, answer: 0, correct: 0 }).initialGrant).toBe(10_000);
  });

  it("誤差 5 は −500 円（誤差 × 100 円）を減算する", () => {
    const r = applyQuestionScore({ balance: 10_000, answer: 45, correct: 50 });
    expect(r.error).toBe(5);
    expect(r.delta).toBe(-500);
    expect(r.balance).toBe(9_500);
  });

  it("誤差 0 はピタリ賞で他プレイヤーから 1,000 円を横取りする", () => {
    const r = applyQuestionScore({ balance: 10_000, answer: 50, correct: 50 });
    expect(r.error).toBe(0);
    expect(r.pitariBonus).toBe(1_000);
    expect(r.currency).toBe("円"); // 点化・ポイント置換は禁止
  });

  it("100 を超える回答は受理しない（0〜100 整数のみ）", () => {
    expect(() => applyQuestionScore({ balance: 10_000, answer: 101, correct: 50 })).toThrow();
  });
});
```

### 2.4 データ入稿・DB・ライブ編集

#### ADR-E-1 — 入稿方法 = 事前ファイル読込（2026-07-28 確定・論点5）

- **決定**: 事前に用意した問題ファイルを読み込む。当日その場入力方式は採らない。論点5 は選択肢 (A) 事前ファイル読込に確定。
- **影響モジュール**: `src/questions/`（ファイル読込 → DB `questions` 登録）。

#### ADR-E-3 — ゲーム中の問題・正解のライブ編集（2026-07-28 確定）

- **決定**: ゲーム進行中も『問題』『正解』の双方を書き換え可能。理由は「その場で正解が決まる問題がある」ため。編集は制御盤（`src/control_panel/`）のライブ編集 UI から行い、**DB 更新**として反映する。
- **影響モジュール**: `src/control_panel/`・`src/questions/`。

#### ADR-E-3残 — 開示済み問題の再採点（2026-08-11 確定・軍師推奨 A 採択）

- **決定**: ライブ編集で正解を訂正した場合、**自動で再採点し残額へ反映する**（司会者が都度選ぶ方式・再採点しない方式は不採用）。
- **「開示済み」の定義**: TV 上で「c 正解発表」を実行した時点以降＝正解値が観客へ出た後の状態。b（解答オープン）までしか進んでいない問題は「開示済み」ではない。
- **「直し」の定義**: 正解値が観客へ出た後に正解を訂正すること。c より前の正解入力/修正は通常のライブ編集で本論点の対象外。
- **d まで進んでいた場合**: 自動再採点に加え**残額の差分再計算**を伴い、TV の **d（得点精算）・e（全員一覧）を同時更新**する。
- **影響モジュール**: `src/game_state/`（問題ごとに b/c/d のどこまで進んだかを保持）・`src/scoring/`（差分再計算）・`src/realtime_sync/`（TV d/e の同時反映）。
- **帰結**: `game_state` テーブルは各 `question_id` の進行段階（`answers_opened`/`answer_revealed`/`settlement_computed`）を保持し、この段階判定なしに再採点範囲は決定できない。

#### ADR-N-2 — 出題動画の実体・入稿方法（2026-08-13 確定）

- **決定**: 問題ファイルに**動画ファイルパスを記載**し、動画は**所定フォルダへ事前配置**する（全問動画必須・動画なし a モード静止のみ、は不採用）。
- **フォールバック順**: **動画 →（無ければ）画像出題画面 →（無ければ）テキスト出題画面**の3段（従前「テキスト直行」を更新し画像を第1フォールバックとして挿入）。
- **影響モジュール**: `src/questions/`・`src/tv_display/`（a モードの出題面解決）。問題データは動画パス・画像パス（任意）・テキストを保持する構造とする。

### 2.5 提示・UI

#### ADR-第三要件 — タブレット入力専用・TV 5モード MC 切替（2026-07-31 確定・従前想定に優先）

- **決定**:
  1. 入力デバイス = タブレット（**入力専用**）。スタジオ提示には使わない。
  2. TV（メイン表示）は MC の合図で **5 モードを切り替える**。切替操作は操作盤（`src/control_panel/`）側から行う: **a 出題動画／b 解答者の解答オープン／c 正解発表／d 1問ごとの得点精算／e 現在の解答者全員の得点一覧**。
- **旧記述の上書き**: 第二要件「スマホで回答」→タブレット入力／「各解答者のタブレットへ開示」→**廃止**（開示は TV の b のみ）／「入力=スマホ・確認=タブレット」の2端末役割分担→**廃止**（タブレット1台＝入力専用）。第一要件の骨格（ノート PC=制御盤・HDMI 拡張で TV 表示・司会者進行）と論点7 は不変。
- **影響モジュール**: `src/tablet/`・`src/tv_display/`・`src/control_panel/`。

#### ADR-論点8 — 表示レイアウト（2026-07-31 廃止）

- **廃止**: 旧論点8（タブレット=自分中心／TV=常に全員一覧）は第三要件により解決・消滅。タブレットは提示に使わず、TV は常時一覧でなく MC 切替の5モード制。判断不要。

#### ADR-F — 正解発表の演出 = MVP 最小限（2026-07-28 確定・論点6）

- **決定**: MVP では演出は最小限。まず動くものを優先し、効果音・カウントダウン・アニメ・ランキング演出は MVP 後の拡張候補（過剰実装禁止）。
- **適用**: MVP の正解発表は**開示一覧＋正解値＋得点増減（円）の表示まで**（得点方式=案A ゆえ増減表示は必須級）。
- **影響モジュール**: `src/tv_display/`（c モード）。

#### ADR-N-3 — MC 切替 UI の操作単位（2026-08-14 確定）

- **決定**: 操作盤は **3系統**を備える: ① 順送り「次へ」 ② 「戻る」（前モードへ・殿御追加） ③ 各モード（a〜e）への個別ジャンプボタン。5モード間を順送り・逆送り・任意ジャンプの3経路で切り替える（個別のみ/順送りのみは不採用）。
- **影響モジュール**: `src/control_panel/`・`src/realtime_sync/`（`src/tv_display/` へモード変更を配信）。

#### ADR-N-1 — タブレット画面の表示範囲（2026-08-15 確定）

- **決定**: **入力専用の最小 UI**。表示要素は以下に限る:
  - 現在の**問題番号**
  - **数値入力**（回答入力欄）
  - **送信済み表示**（自分が送信した解答の確認）
  - **自分の残額**（★殿御追加。自分の現在残額のみ。他者の残額・得点・解答は出さない）
- **入力方式**: **+1 / −1 / +10 / −10 の4ボタン方式**（テンキー直接入力ではない）。0〜100 の整数のみを4ボタンで増減（G と整合）。
- **影響モジュール**: `src/tablet/`。出題内容の提示・他者情報・全体一覧は TV 側の役割でタブレットには出さない（第三要件と整合）。

#### ADR-N-4 — d「1問ごとの得点精算」の表示内容（2026-08-15 確定・`module:scoring` の可視化）

- **決定**: TV の d モードは**当該問の全員表**を表示する。**6列**構成: **氏名 / 解答 / 誤差 / 増減円 / ピタリ賞 / 残額**。
  - 誤差 = |解答 − 正解|（0〜100 の整数）
  - 増減円 = 誤差 × −100 円（ピタリ賞成立時は他プレイヤーからの +1,000 円も反映）
  - ピタリ賞 = 誤差0 の該当有無
  - 残額 = 当該問精算後の各人の現在残額
- **役割分担**: **d は当該問フォーカス／e は全問通算**。
- **影響モジュール**: `src/tv_display/`（d モード）・`src/scoring/`。**リリースブロッキング不変条件2** の可視化にあたり、増減円・ピタリ賞・残額は確定値どおり「円」で表示する。

### 2.6 進行制御・権限

#### ADR-論点7 — 締切・開示・取消の権限（2026-07-30 確定）

- **決定**: **締切（「そこまで」＝ `answers_locked`）・開示（「解答オープン！」＝ `answers_opened`）ボタンの発動は司会者（制御盤 `role: host`）のみ**。副司会・解答者端末からは押せない。
- **取消**: 押し間違いの**取り消しも司会者（制御盤）のみが発動できる操作として初版から含める**（`trigger_undone`）。★軍師の当初推奨「取り消し・再回答は初版で作らない」から一点変更＝殿仰せ優先。
- **未確定の扱い**: 取り消しの具体挙動（直近操作のみ戻せるか／任意問題を再開示できるか等）に曖昧が残れば、**推測実装せず F028 で選択肢を添えて殿判断**を仰ぐ（→ §3.2）。
- **影響モジュール**: `src/control_panel/`・`src/game_state/`・`src/realtime_sync/`。TV 5モード切替も「操作盤側から」で論点7 と整合。
- **アクセス制御（具体）**: `answers_locked`/`answers_opened`/`answer_revealed`/`trigger_undone` を発火できるのは `role: host` セッションに限定し、`role: answerer` からの当該コマンドはサーバ側で拒否する。

### 2.7 参加登録・接続上限（`module:participants` / `module:config`）

#### ADR-論点9改 — 参加登録と端末の紐付け（2026-08-11 確定）

- **決定**: **ホスト画面に表示する QR をタブレットで読み取り、氏名を自己入力する**方式（`/join`）。**1人 = 1台のタブレット（入力専用）**。対案『端末番号の固定割当』は不採用。
- **含意**: 参加用 URL は**クラウド公開 URL**であり QR はこれを指す（2026-08-08 クラウド前提と整合）。事前の座席・氏名登録は不要で、参加者の増減は当日その場で吸収する。
- **影響モジュール**: `src/participants/`（DB `participants`）・`src/control_panel/`（QR 表示）。
- **記録（後付け理由の禁止）**: なりすまし・取り違え耐性は本推奨の根拠として検討・記録していない。必要なら別途論点として立てる。

#### ADR-論点10 — 同時接続タブレット上限（2026-08-11 確定・release-blocking 不変条件3）

- **決定**: **既定値 = 8 台**（家族規模）。★設計制約: **上限値のハードコードを禁止**。上限は設定値/コンフィグとして外出しし、将来 8→16→32 等へ**非改修で変更可能**とする。
- **実装要件**:
  - 上限値は設定パラメータ（`MAX_TABLET_CONNECTIONS`）として定義し、アプリ起動時/デプロイ時に与えられること。コード中に定数リテラル `8` を埋め込まない。
  - **上限超過時の挙動（接続を断る）は上限値の変更に追随**すること（上限判定は設定値を参照）。
  - 同期基盤（`src/realtime_sync/` のクラウド WebSocket）は8台を前提に最適化しつつ、**設定変更で32台程度まで引き上げても破綻しない**ことを選定軸に含める。
  - 設定の具体的な持ち方（環境変数／設定ファイル／DB 設定テーブル）は greenfield 時に選定（→ §3.1）。ハードコード禁止の要件のみが確定。
- **影響モジュール**: `src/config/`（上限値の解決）・`src/participants/`（接続受け入れ判定）。
- **帰結（release-blocking）**: 上限は `src/config/` が単一の解決点となり、`src/participants/` はその値を参照して超過接続を拒否する。受け入れは以下の Vitest テストで固定する。

```typescript

    expect(resolveMaxTabletConnections()).toBe(8);
  });

  it("設定 32 を非改修で反映する（8→16→32 への引き上げ）", () => {
    process.env.MAX_TABLET_CONNECTIONS = "32";

  });
});
```

## 3. Follow-ups

壁打ち（要件定義）フェーズはクローズ済で殿判断待ちの論点は残っていない。以下は実装組み立てフェーズで MAS 側が決める技術選定と、実装時に曖昧が生じた場合のエスカレーション経路、および検証計画である。

### 3.1 greenfield 実装時の技術選定（殿判断不要・MAS が決定）

| 項目 | 内容 | 制約・選定軸 |
|---|---|---|
| ホスティング/インフラ | どのクラウドで・常時稼働かイベント時のみか・費用・レイテンシ | **当日インターネット接続前提**で稼働し、クラウド WebSocket に対応すること。ホスト PC をサーバにしない（不変条件1）。回線断は運用側でバックアップ回線/テザリング等により当日回線を確保し、コードは当日接続前提で組む。 |
| DB 永続化技術 | `questions`・`answers`・`participants`・`balances`・`game_state` を保持する DB | クラウド実行と整合すること。ファイル読込→`questions` 登録、ゲーム中のライブ編集（DB 更新）、E-3残 の進行段階保持を満たすこと。 |
| 実装言語 | — | **TypeScript / Node に解決済**（要件の選定軸「クラウドへデプロイでき WebSocket 等を扱える」に一致・本書 §1.4 の scaffold と整合）。テストランナーは Vitest 固定、モジュール解決は NodeNext/Node16。 |
| 家族限定アクセス制御 | URL を知る者のみか／認証を設けるか | 参加ベクタは QR が指すクラウド公開 URL（`/join`）。決定は保留だが、当面のブラスト半径抑制策として **接続上限（`MAX_TABLET_CONNECTIONS`・既定8）** と **トリガー権限の司会者限定（論点7）** が有効。認証方式を導入する場合も上限判定・権限判定の単一解決点（`src/config/`・`role: host` チェック）を経由させる。 |
| 上限設定の持ち方 | 環境変数／設定ファイル／DB 設定テーブル | いずれでも可だが `src/config/` が唯一の解決点となること。ハードコード禁止（不変条件3）。デフォルトの具体機構は環境変数 `MAX_TABLET_CONNECTIONS` を採る。 |

### 3.2 F028 エスカレーション対象（推測実装しない）

- **取り消し操作の具体挙動（論点7）**: 直近操作のみ戻せるのか／任意の問題を再開示できるのか等に曖昧が残る場合は、選択肢を添えて F028 で殿判断を仰ぐ。実装で勝手に確定しない。
- **ピタリ賞の分配詳細（B）**: 「他プレイヤーから 1,000 円を獲得」の獲得額は 1,000 円で確定だが、複数同時ピタリ時や誰から幾ら差し引くかの分配割りに曖昧が生じた場合は F028 で選択肢提示。確定値（1,000 円・円建て・現金感を薄めない）は変更しない。

### 3.3 検証（Vitest）計画と受け入れ観点

verify コマンドは Vitest を実行し、テストは `tests/` 直下のみを探索する。以下を release-blocking 不変条件の受け入れとして固定する（依存最小化の方針があってもテストランナーは Vitest から動かさない）。

| テストファイル（`tests/` 下） | 対象モジュール | 検証内容 |
|---|---|---|
| `tests/scoring.test.ts` | `src/scoring/` | 先渡し10,000円・誤差×−100円・ピタリ賞1,000円・円建て（点化しない）・0〜100 整数拒否（不変条件2） |
| `tests/connection_limit.test.ts` | `src/config/` | 既定8・設定で32へ非改修反映（不変条件3） |
| `tests/admission.test.ts` | `src/participants/` | 上限到達で接続拒否・上限引き上げに追随（不変条件3） |
| `tests/rescoring.test.ts` | `src/scoring/`・`src/game_state/` | 「開示済み」= c 実行以降の自動再採点・d 到達時の残額差分再計算 |
| `tests/game_state.test.ts` | `src/game_state/` | 問題ごとの b/c/d 進行段階の保持・トリガー権限が `role: host` に限定 |

すべてのテストは Vitest の宣言 API（`import { describe, it, expect } from "vitest";`）で記述し、`src/` へは `.js` 拡張子付きの相対 import（例: `../src/scoring/apply_question_score.js`）で参照する。テストは `tests/` 外に置かない・ランナー/ツール設定（`package.json`・`package-lock.json`・`tsconfig.json`・`vitest.config.ts`）はハーネス所有ゆえ本フェーズでも著さない。
